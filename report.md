# Отчёт по проекту Ferrous

Ferrous — компилятор собственного языка программирования (`.fer`):
лексический анализ → синтаксический анализ → семантический анализ → генерация
кода через LLVM IR. Документ описывает архитектуру, принятые проектные решения,
зафиксированные развилки семантики и список выполненных дополнительных заданий.

## 1. Архитектура компилятора

```
Исходный .fer
    ↓
[Lexer]    (mod/lexer.cppm,    src/lexer.cpp)     — поток токенов с (line, column)
    ↓
[Parser]   (mod/parser.cppm,   src/parser.cpp)    — AST: vector<Decl>
    ↓
[Semantic] (mod/semantic.cppm, src/semantic.cpp)  — AnnotatedAST + DiagBag
    ↓
[Codegen]  (mod/codegen.cppm,  src/codegen.cpp)   — LLVM IR → clang++ → бинарь
    ↓
Исполняемый файл
```

Каждая фаза — отдельный модуль C++20 в собственном `namespace` (`Lexer::`,
`Parser::`, `Semantic::`, `Codegen::`), и фазы намеренно изолированы друг от
друга: парсер знает только про `Token`, семантика — только про AST, кодоген —
только про `AnnotatedAST`. Благодаря этому каждую фазу можно читать, тестировать
и менять, не держа в голове остальные.

## 2. Проектные решения

### 2.1. Модули C++20 

Все фазы оформлены как модули: интерфейс в `export module Ferrous.X`,
реализация — в отдельной единице (`module Ferrous.X;` без `export`). Стандартная
библиотека подключается обычными `#include` в глобальном фрагменте модуля
(`module;`), **без `import std`** — так проект собирается любой реализацией
stdlib (libstdc++/libc++) и любым компилятором с поддержкой модулей. 

### 2.2. AST на `std::variant` + `std::visit`

Каждый узел дерева — простая структура-данные, а `Expr` / `Stmt` / `Decl` —
обёртки с полем-`variant` `node`. Обход реализован через `std::visit` с лямбдой
и диспетчеризацией по `std::is_same_v<T, …>` — это даёт эффект паттерна Visitor
без единого `virtual`. Дочерние узлы хранятся как `std::unique_ptr<Expr>` для
рекурсии, `std::vector<Expr>` для списков и `std::optional<TypeRef>` для
необязательных частей.


### 2.3. Двухпроходная семантика

- **Проход 1** обходит только верхнеуровневые декларации и регистрирует имена:
  структуры и псевдонимы (через placeholder + отдельный проход для полей, чтобы
  работали взаимные ссылки), функции с их перегрузками, пространства имён
  (рекурсивно).
- **Проход 2** проверяет тела функций, ведя стек областей видимости.

Разделение на два прохода даёт forward-ссылки для функций и типов верхнего
уровня — это прямо требуется ТЗ (раздел «Разрешение имён») и спекой.

### 2.4. Обоснование выбора подходов

**Метод синтаксического разбора — рекурсивный спуск + Pratt.** Декларации и
инструкции разбираются обычным рекурсивным спуском: их грамматика регулярна
(ведущее ключевое слово `fn`/`struct`/`let`/`if`/… однозначно задаёт правило),
поэтому спуск читается один-к-одному с грамматикой и легко восстанавливается
после ошибок (синхронизация по `;` и границам инструкций).
Выражения же со спуском вырождаются в лестницу из десятка функций
(`parse_add → parse_mul → …`) на каждый уровень приоритета. Поэтому для выражений
взят **Pratt-парсер** (доп B.1.4): один `parse_expr(min_prec)` с таблицей
приоритетов и ассоциативности вместо отдельной функции на уровень. Добавить
оператор или поменять приоритет — это правка одной строки таблицы, а не новая
функция. Генераторы парсеров (`bison`/`antlr`) ТЗ запрещает, так что выбор был
между ручными методами, и эта связка покрывает обе части грамматики минимальным
кодом.

**Платформа генерации кода — LLVM IR.** ТЗ допускает три пути: нативный код
x86-64, LLVM IR или интерпретацию. Выбран LLVM IR по нескольким причинам:

- *Переносимость и корректность.* Не нужно вручную писать кодирование инструкций,
  System V ABI, аллокацию регистров и стековые фреймы — это делает LLVM. Учебный
  компилятор фокусируется на фронтенде (лексер/парсер/семантика), а не на тонкостях
  бэкенда конкретной архитектуры.
- *Верификация.* `verifyModule` ловит некорректный IR ещё до линковки — это
  поймало целый класс рассогласований семантики и кодогена на этапе разработки.
- *Готовый рантайм-мост.* IR компилируется и линкуется штатным `clang++` вместе с
  маленькой рантайм-библиотекой (`rt/ferrous_rt.cpp`: печать, проверки границ,
  panic/assert, преобразования строк). Это дешевле, чем собственный ассемблерный
  пролог/эпилог и обвязка ввода-вывода.
- *Текстовый IR как побочная польза.* Рядом с бинарём кладётся `<out>.ll` —
  человекочитаемый дамп, удобный для отладки кодогена.

Интерпретация отвергнута, так как ТЗ требует именно нативный исполняемый файл;
прямая генерация x86-64 — как чрезмерно трудоёмкая для учебного срока при том, что
она не добавила бы новых возможностей языку.

## 3. Выполненные дополнительные задания

### Реализованы полностью

| Код        | Задание                            | Как реализовано                                                       |
|------------|------------------------------------|----------------------------------------------------------------------|
| **A.1.1**  | Числовые типы 8–64 бит             | `int8…int64`, `uint8…uint64`, `float32/64`; суффиксы (`42i8`, `7u32`, `1.0f32`), hex/bin-литералы (`0xFF`, `0b1010`). |
| **A.1.8**  | Неявное приведение типов           | Единая таблица расширений (`types.md` §6.1) во всех контекстах: `let`/`=`/`op=`/`return`/элемент массива/поле структуры (helper `coerce_to`) и бинарные операторы (общий тип, `common_type`). Допустимы целое→шире той же знаковости, `float32→float64`, целое→float при точной представимости; сужение/смена знака — ошибка (нужен `as`). Касты вставляются централизованно в кодогене (`gen_expr` → `gen_num_cast` по карте `coerce`). Та же таблица питает стоимостную модель перегрузки A.3.1. *(Учётный лимит уровня 1 уже исчерпан — задание реализовано для цельности языка.)* |
| **A.1.9**  | Расширенные операторы              | Битовые `& \| ^ ~ << >>` для целых; величина сдвига берётся по модулю ширины типа (`amt & (w−1)`), поэтому сдвиг ≥ ширины и отрицательный сдвиг определены; `>>` арифметический для знаковых, логический для беззнаковых. Составные присваивания `+= -= *= /= %= &= \|= ^= <<= >>=` (адрес lhs вычисляется один раз; `+=` для строк — конкатенация). |
| **A.1.15** | Блочные комментарии с вложенностью | `/* … /* … */ … */` корректно считает уровень вложенности.            |
| **A.2.8**  | Перегрузка функций                 | Несколько функций с одним именем; разрешение по точному совпадению типов **без неявных приведений** (ровно как требует пункт), с особой обработкой нетипизированных литералов. Манглинг имён в кодогене. |
| **A.2.9**  | Параметры по умолчанию + именованные аргументы | Дефолты-литералы только в хвосте параметров; вызов по позиции и по имени (`box(h=3, w=2)`), перестановка хвостовых параметров; интеграция с перегрузкой (раскладка по слотам для каждого кандидата, дефолт = точное совпадение). Кодоген генерит аргументы в порядке параметров через аннотацию `call_slots`. Диагностики: дефолт не в хвосте, неизвестное/дублирующее имя, позиционный после именованного. |
| **A.3.1**  | Перегрузка функций с неявными приведениями типов | Расширение стоимостной модели на типизированные аргументы: расширение целого той же знаковости (10 + шаги ширины), `float32→float64` (10), целое→вещественное при точной представимости (20); запрет сужения, смены знака и 64-бит→float. При равной минимальной стоимости — ошибка `ambiguous call` со списком кандидатов. Кодоген вставляет неявный каст (`gen_num_cast`, общий с `as`, через единую карту `coerce` — см. A.1.8) и манглит по типам параметров перегрузки (аннотация `call_slot_types`). **Пара A.2.8 ↔ A.3.1** (расширяет). |
| **B.1.1**  | Восстановление после синтаксических ошибок | Парсер синхронизируется на границе инструкции и копит несколько диагностик за запуск; одна пропущенная `;` даёт одну ошибку, а не каскад. |
| **B.1.4**  | Pratt-парсер выражений             | Единый `parse_expr` с таблицей приоритетов и ассоциативности (см. §2.3). |


Базовые требования ТЗ покрыты: целые/вещественные/`bool`/`char`/`string`, массивы
фиксированного размера, структуры, псевдонимы типов, пространства имён, функции с
перегрузкой, полный набор операторов и управляющих конструкций, runtime-проверки
(деление/остаток на ноль, выход за границы, `panic`/`assert`) в требуемом формате.

## 4. Зафиксированные решения по развилкам семантики

| #  | Развилка                                                | Решение                              |
|----|---------------------------------------------------------|--------------------------------------|
| S1 | Тип возврата `main`                                     | Строго `int32`                       |
| S2 | Локальная переменная затеняет параметр                  | Запрещено (`duplicate variable`)     |
| S3 | `while true { return X; }` — возвращает всегда?          | Да, если из цикла нет `break`        |
| S4 | Рекурсивные структуры по значению                       | Запрещены (бесконечный размер)       |
| S5 | Массивы нулевого размера                                | Запрещены                            |
| S6 | `void main`                                             | Запрещено                            |
| S7 | Неявные числовые преобразования при `=`/`let`/операторах | Разрешены расширения (widening), A.1.8 |
| S8 | Литерал вне диапазона целевого типа                     | Ошибка компиляции                    |
| S9 | int-литерал в float-контексте (`let x: float64 = 1`)    | Разрешён (литерал подстраивается)    |

**Детализация.**

- **S1 / S6.** Программа обязана содержать ровно одну `fn main() -> int32`; её
  возвращаемое значение становится кодом завершения процесса. Любая другая
  сигнатура `main` — ошибка семантики.
- **S2.** Параметры и локальные переменные тела функции живут в одной области
  видимости, поэтому `let`, повторяющий имя параметра, — это `duplicate variable`.
  Затенение разрешено только во вложенном блоке `{ … }`, который открывает свой
  scope. При этом тело функции из namespace видит соседей по своему пространству
  имён, потому что его scope подвешен к scope namespace, а не к корню.
- **S3.** `always_returns` распознаёт литерал `true` в условии `while`:
  бесконечный цикл без достижимого `break` никогда не «проваливается» дальше,
  поэтому функция считается возвращающей. Появление `break` это свойство снимает.
- **S4.** `struct A { x: A }`, взаимная рекурсия `A→B→A` и рекурсия через массив
  фиксированного размера — все запрещены: при семантике значений без указателей
  это означало бы бесконечный размер.
- **S5.** `[T; 0]` — ошибка `array size must be positive` ещё на `resolve_type`.
  Пустой литерал `[]` без аннотации — `cannot infer type of empty array`.
- **S7 / S8 / S9.** Неявные **расширения** (widening) разрешены во всех
  контекстах по единой таблице (A.1.8, `types.md` §6.1): `let b: int64 = a_i32;`
  и `a_i32 + b_i64` корректны (узкий операнд расширяется). А вот **сужение**
  (`int8 = int64`) и **смена знака** (`int32 + uint32`) — ошибка компиляции,
  нужен явный `as`: это защищает от молчаливой потери данных.
  Нетипизированный литерал (`42`, `3.14`) подстраивается под контекст с проверкой
  диапазона: `let x: int8 = 300` и `let s: string = 42` отвергаются. int-литерал
  допускается в вещественный контекст (кодоген эмитит FP-константу), но не наоборот.

## 5. Встроенные функции и операции

| Функция / операция          | Сигнатура                          | Примечание                          |
|-----------------------------|------------------------------------|-------------------------------------|
| `len(s)` / `len(arr)`       | `string→int32`, `[T;N]→int32`      | длина строки / статический размер    |
| `to_string(x)`              | числовые + `bool` → `string`       | преобразование через рантайм         |
| `to_int(s)` / `to_float(s)` | `string→int64` / `string→float64`  | некорректный ввод → 0                |
| `a + b` (строки)            | `string, string → string`          | конкатенация                         |
| `a == b` / `a != b`         | строки, массивы, структуры         | поэлементное сравнение (рекурсивно)  |
| `print` / `println(x)`      | любой тип → `void`                 | перегрузка по типу аргумента         |
| `input()`                   | `→ string`                         | строка из stdin                      |
| `panic(msg)` / `assert(c)`  | прерывание с диагностикой          | формат `runtime error: … at line N`  |
| `exit(code)`                | `int32 → void`                     | через рантайм `__ferrous_exit`       |

## 6. Сборка, запуск, тесты

### Зависимости

- CMake ≥ 3.30, Ninja
- clang ≥ 17 (или g++ 16+) с поддержкой C++23 и модулей C++20
- системный LLVM ≥ 17

### Сборка

```bash
cmake --preset clang     # конфигурация в каталог build/
cmake --build build      # бинарь build/Ferrous
```

### CLI

```
./build/Ferrous <source.fer> [--dump-tokens|--dump-ast|--dump-sema] [-o <out>]
```

| Флаг            | Что делает                                              |
|-----------------|--------------------------------------------------------|
| `--dump-tokens` | Печатает поток токенов и завершает работу.             |
| `--dump-ast`    | Печатает AST и завершает работу.                       |
| `--dump-sema`   | Печатает AST с выведенными типами на каждом выражении. |
| `-o <out>`      | Имя выходного исполняемого файла.                      |
| без флагов      | Полный pipeline до исполняемого файла.                 |

Без `-o` имя выходного файла берётся из имени исходника (`foo.fer` → `foo`).

```bash
./build/Ferrous examples/test_arithmetic.fer        # → ./test_arithmetic
./build/Ferrous examples/test_functions.fer --dump-ast
```

### CMake-цели

| Цель    | Что делает                                              |
|---------|--------------------------------------------------------|
| `build` | Стандартная сборка (по умолчанию).                     |
| `run`   | Компилирует пример и **исполняет** полученный бинарь.  |
| `debug` | Прогоняет диагностические фазы (tokens/ast/sema).      |
| `check` | Запускает весь набор тестов (`run_tests.sh`).          |
| `clean` | Встроенная цель сборочной системы.                     |

### Тесты

`run_tests.sh` (или цель `check`) прогоняет каталог `examples/` по трём
категориям:

- `test_*.fer` — позитивные: компилируются и исполняются с кодом 0;
- `err_sema_*.fer` — ошибки **компиляции**: компилятор отвергает программу
  (код 1), а его диагностика сверяется с маркером `// @error: …` из первой строки
  файла;
- `err_*.fer` (остальные) — рантайм-ошибки: компилируются, но исполнение даёт
  ненулевой код (деление/остаток на ноль, выход за границы, `panic`, `assert`).
